# How downstream systems consume an extracted Knowledge Graph

Research for [#137](https://github.com/JoaZaech/stetiq/issues/137), part of the map [#135](https://github.com/JoaZaech/stetiq/issues/135). Terms follow `GLOSSARY.md` (Consumer, Task, Consumer Gate, Connector). Constraints: no instance data (ADR 0001), and Connectors live at the Consumer's edge while the core computes over artifacts (ADR 0005).

## Short answer

Five kinds of Consumer show up in first-party docs. They differ in **where the Ontology is written down on the Consumer's side**:

1. **Hand-written Cypher** in an application, a GraphRAG retriever's `retrieval_query`, a Cypher template or a dashboard report. The Ontology is baked into query strings. Removing or renaming a label, Relation or Attribute does not raise an error: Neo4j only emits a *warning* (`UnknownLabelWarning` and similar) and the query returns nothing.
2. **Text2Cypher and agents** (LangChain `GraphCypherQAChain`, LlamaIndex `TextToCypherRetriever`, neo4j-graphrag `Text2CypherRetriever`, the Neo4j MCP server). The Ontology is a **schema string in the LLM prompt**, usually sampled live from the database. The query adapts to a change, but few-shot examples, prompt wording and the Task's quality do not, so it degrades without failing.
3. **Typed API layers** (Neo4j GraphQL Library). The Ontology is declared in type definitions (`@node`, `@relationship(type:…)`, `@alias`). It breaks like the hand-written Cypher above, but the type definitions are a checkable artifact.
4. **Microsoft GraphRAG-style indexes.** The graph is flattened into tables (entities with a free-text `type`, relationships, communities, reports) and read back through vector and community search. Coupling to the Ontology is loose, so changes surface as shifts in answer quality, not as errors.
5. **BI and dashboards** (NeoDash and similar). Each report is one Cypher query, so this is case 1 in a different place.

**Recommended first Connector:** a **CI check in the Consumer's repository**. It extracts the Consumer's Cypher (application code, `retrieval_query`s, templates, Competency Question queries) and lints it against a target Ontology Version, or an Alias, using Neo4j's own Cypher language-support library. The Consumer Gate's verdict then fails the build. It is deterministic, never touches instance data, and covers kinds 1, 3 and 5, plus the GraphRAG retrievers that use Cypher.
**Second:** an **MCP schema server** that gives agents and Text2Cypher (kind 2) the Contract Alias's Ontology, with Definitions, Deprecations and Vocabularies, in place of a sampled schema. It notifies subscribers on Promotion. This is a strong demo for the pitch, and it could be shown as planned if it does not make the MVP.

## Consumer kinds

### 1. Applications and retrievers with hand-written Cypher

- **Depends on:** label names, relationship types and directions, and property keys, all literal in query strings. In the neo4j-graphrag Python package, `VectorCypherRetriever` and `HybridCypherRetriever` take a user-written `retrieval_query` that traverses named labels and relationships after the vector or full-text search. The docs' examples use `Actor`, `ACTED_IN` and `AUTHORED_BY`. Vector retrievers also depend on index names and, for in-index filtering, on `filterable_properties`. Sources: [neo4j-graphrag RAG user guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html). LlamaIndex's `CypherTemplateRetriever` puts the schema in a fixed Cypher template whose parameters an LLM fills in. Source: [LlamaIndex property graph guide](https://developers.llamaindex.ai/python/framework/module_guides/indexing/lpg_index_guide/).
- **How it breaks:** silently. Neo4j reports a label, relationship type or property key that is not in the database as `Neo.ClientNotification.Statement.UnknownLabelWarning` / `UnknownRelationshipTypeWarning` / `UnknownPropertyKeyWarning` (GQLSTATUS 01N50/01N51/01N52), all at severity **WARNING**. That is a notification, not an error, so the query runs and matches nothing. Source: [Neo4j status codes, all notifications](https://neo4j.com/docs/status-codes/current/notifications/all-notifications/). A breaking Ontology Diff therefore shows up as empty results or a thin RAG context, not as an exception. Deprecations do not reach the Consumer unless someone tells it.
- **What a Connector can plug into:** the Consumer's own **CI**, before deploy. Neo4j's `@neo4j-cypher/language-support` library lints a query against a supplied `DbSchema` (`languageService.lint(query, schema)`). Its validator reports a label or relationship type missing from that schema as "is not present in the database". Sources: [language-support README](https://github.com/neo4j/cypher-language-support/tree/main/packages/language-support), and the message text in [`syntaxValidation.ts`](https://github.com/neo4j/cypher-language-support/blob/main/packages/language-support/src/syntaxValidation/syntaxValidation.ts) and its tests. A Connector can build the `DbSchema` from an **Ontology Version** rather than from a live database. The check then runs offline against the version about to be promoted, needs no database credentials, and never sees instance data. Both ADRs are satisfied.

### 2. Text2Cypher chains and agents (incl. via MCP)

- **Depends on:** a **schema string injected into the prompt**. LangChain's `Neo4jGraph` builds it from the database. `refresh_schema()` is the call to make "if the schema of database changes", `enhanced_schema=True` samples example values and distributions, and `GraphCypherQAChain`'s prompt says "Use only the provided relationship types and properties in the schema". `include_types`/`exclude_types` trim the schema, and `validate_cypher` corrects relationship directions. Source: [LangChain Neo4j guide](https://docs.langchain.com/oss/python/integrations/graphs/neo4j_cypher.md). LlamaIndex's `TextToCypherRetriever` "uses a graph store schema, your query, and a prompt template" ([LlamaIndex guide](https://developers.llamaindex.ai/python/framework/module_guides/indexing/lpg_index_guide/)). neo4j-graphrag's `Text2CypherRetriever` takes a `neo4j_schema` string and optional `examples`, and warns that the generated query "is not guaranteed to be syntactically correct" ([neo4j-graphrag guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)). Agents reach the graph through the Neo4j MCP server, whose tools are `get_neo4j_schema`, `read_neo4j_cypher` and `write_neo4j_cypher`. Its schema comes from APOC `apoc.meta.schema`, **sampled** at 1000 nodes per label by default. Source: [mcp-neo4j-cypher](https://github.com/neo4j-contrib/mcp-neo4j/tree/main/servers/mcp-neo4j-cypher).
- **How it breaks:** softly. If the schema is read live, generated queries follow the new structure. But a cached schema string, hand-written few-shot `examples` and prompt instructions go stale, and the schema the LLM sees is *observed* (sampled, with no Definitions, no Deprecations and no closed Vocabularies), not *declared*. A rename the LLM cannot map, or a Relation whose meaning changed without its name changing, lowers answer quality without any error. That is exactly what executed Competency Questions are meant to catch.
- **What a Connector can plug into:** (a) **The prompt's schema source.** A stetiq-backed MCP server or retriever schema provider would serve the Ontology Version behind an Alias, with Definitions, Alternative Labels, Deprecations and Vocabularies, which is richer than `apoc.meta.schema`. MCP gives a native change signal: servers can declare `resources.subscribe` and send `notifications/resources/updated` when a resource changes ([MCP spec, resources](https://modelcontextprotocol.io/specification/2025-06-18/server/resources)), so a Promotion can reach subscribed agents. (b) **Few-shot examples in CI**, linted the same way as kind 1.

### 3. Typed API layers (GraphQL over the graph)

- **Depends on:** type definitions that "describe the shape of your graph data". `@node` maps a type to a node, `@relationship(type:, direction:)` names the relationship type, and `@alias` maps a field to a property. Each request becomes "a single Cypher query". Sources: [Neo4j GraphQL Library](https://neo4j.com/docs/graphql/current/), [directives](https://neo4j.com/docs/graphql/current/directives/).
- **How it breaks:** the same way as kind 1, because the generated Cypher hits unknown labels or types and returns nothing.
- **What a Connector can plug into:** CI. The type definitions are a declarative artifact, so a Connector can diff their labels, relationship types and properties against an Ontology Version. This is a variant of the Cypher lint Connector, with a different extractor.

### 4. Microsoft GraphRAG-style indexes

- **Depends on:** output tables, not a typed graph. `entities` has `title`, a plain-string `type`, `description` and `degree`. `relationships` has `source`, `target`, `description` and `weight`. On top of these sit `communities`, `community_reports` and `text_units`. The default entity types are organization, person, geo and event, unless they are configured or auto-tuned. Sources: [GraphRAG outputs](https://microsoft.github.io/graphrag/index/outputs/), and `extract_graph.entity_types` in [GraphRAG config](https://microsoft.github.io/graphrag/config/yaml/). Local, global, DRIFT and basic search read entities, relationships, community reports and text units through vector embeddings and ranking parameters (same config page).
- **How it breaks:** semantically, not structurally. A changed entity type list or extraction prompt shifts which entities and relations exist and how they cluster into communities. Retrieval still runs, but answers change. Relationships carry no type, so stetiq's Relation-level Diff applies only partly.
- **What a Connector can plug into:** the **re-index step**, where the user's pipeline runs GraphRAG's indexer. A Connector there runs the Consumer's Competency Questions and Consumer Gate before the new index replaces the old one. This is weaker evidence for stetiq, because the Ontology is thin (types are free text, there are no relationship types) and the signal comes mostly from executed Competency Questions, not from the Diff.

### 5. BI, analytics and dashboards

- **Depends on:** Cypher per report. In NeoDash, "each report will have a single Cypher query behind it" whose results must fit the report type ([NeoDash reports](https://neo4j.com/labs/neodash/2.4/user-guide/reports/)). Exports to SQL/BI tools depend on the same labels and properties.
- **How it breaks:** the same way as kind 1: empty tiles or charts, no error.
- **What a Connector can plug into:** the same Cypher lint, run over the dashboard definition. Dashboards are often edited in a UI rather than in a repository, which makes them a weaker first target than application code.

## Implications for stetiq

- **The shared failure mode** is that a removed or renamed Concept fails *silently* at the Consumer (Neo4j warns, it does not error), and that Deprecations never reach the Consumer. This is the pain stetiq's Consumer impact and Consumer Gate address, and it is the moment for a demo: show the Consumer's build going red on a breaking Ontology Diff before Promotion, where today it would return empty results in production.
- **No instance data and no core-side connection:** both recommended Connectors run in the Consumer's process and consume artifacts: an Ontology Version or Alias, Consumer impact and the Consumer Gate result. This fits ADR 0001 and ADR 0005.
- **Competency Questions with a `query`** are already Cypher. The same linter can check them against a Candidate before it is executed, which is useful upstream too, at the Gate.

## Recommendation

1. **Build for the MVP: Cypher CI Connector** (for example a GitHub Action or `stetiq check` in the Consumer's repository). Input: paths or globs of `.cypher` files and string constants, plus the Alias to check against (default `production`, or a named Candidate). It builds a `DbSchema` from the Ontology Version, lints every query, maps each unknown label or type to the Concepts in the Ontology Diff, fetches the Consumer Gate result, and exits non-zero on failure. It also annotates queries that use deprecated Concepts with their replacements. Covers kinds 1, 3 and 5, and the Cypher-based GraphRAG retrievers.
2. **Show as planned, or build if time allows: MCP schema Connector** for agents and Text2Cypher. It serves the declared Ontology with Definitions and Deprecations as a resource and a tool, and on Promotion sends `notifications/resources/updated`. It is a compelling pitch moment (an agent that knows the Ontology changed), but its value is softer and depends on executed Competency Questions to show.

Microsoft GraphRAG-style Consumers are real, but their thin Ontology makes them a poor first showcase.
